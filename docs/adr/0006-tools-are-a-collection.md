# Tools are a collection, and a missing credential costs a capability rather than a startup

**Status:** accepted

Until now HUGO had exactly one tool and the agent knew its name by heart: `ToolLoop` held a `WebSearchTool` field, inlined `[WEB_SEARCH_TOOL_SCHEMA]` into every request, and resolved a call with `if call.name != "web_search"`. Every new capability therefore meant editing the turn loop. We considered a `BaseTool` class with a registration decorator, and rejected it: HUGO's layers already meet at `typing.Protocol` boundaries with no base classes and no registry (`Thinker` is one method wide), and that is what lets a test double be a five-line class instead of a mock. So a tool is now anything satisfying `Tool` — a `schema: ChatCompletionToolParam` and `async invoke(arguments) -> str | ToolFailure` — `ToolLoop` takes a `Sequence[Tool]` and derives both the `tools=` list it sends and the name-to-implementation map it dispatches through from those schemas, and `build_tools()` in `src/hugo/agent/tools/__init__.py` is the single registration point. Adding a capability is one new file under `tools/`, one line in `build_tools`, and one test file, with no edit to `tool_loop.py` or `llm_client.py`. Failures stay *values* on this path, as they already were — an anticipated failure becomes text the model reads on the next pass and paraphrases aloud — with one bit added: `ToolFailure.retryable`, which the tool sets and the loop honours. Classification belongs to the tool because only the tool holds the vocabulary (a timeout can go differently, a rejected credential cannot), which keeps `except httpx.HTTPError` out of the dispatch layer where it sat purely because the one tool happened to use httpx. MCP is the reason the seam is shaped this way rather than around a base class: an MCP server is one connection and N tools, but that plurality resolves at startup — `list_tools()` becomes N adapter objects in the same flat list — so next round adds a construction step and touches nothing in the agent.

The corollary, and the ops-visible change: `orchestrator.run()` no longer raises when `HUGO_TAVILY_API_KEY` is missing. `build_tools` simply doesn't build the tool, logs a warning, and the model never sees a schema for a capability that can't work. This is a deliberate reversal of a fail-fast we wrote on purpose, and it costs something real — a typo'd `~/.hugo_secrets` on dgx1 is now a line in journald rather than a service that refuses to start, and you'd find out the first time you asked for the weather. We accept that because the alternative doesn't survive contact with what comes next: an unreachable MCP server must not veto a robot's startup, and "the tool set is a data question" is only true end to end if a missing dependency subtracts from the set instead of aborting the process. `hugo dev search` keeps its own hard check, because that command is a Tavily diagnostic rather than a path through the tool set.

Giving `MemoryStore` its first consumer makes one accepted limit worth writing down rather than leaving implicit. The facts DB lives at `~/.local/state/hugo/memory.db` under the shared team account `jim`, and its own module docstring says it "doesn't attempt multi-user isolation" — harmless while nothing wrote to it, and not harmless once HUGO remembers things: anyone with account access can read the file, and anyone who says the wake phrase can ask what HUGO knows and hear the answer. This is accepted as-is because HUGO has one user today, and because nothing available is worth building: file permissions protect nothing when everyone logs in as the same account, and encryption at rest with the key in `~/.hugo_secrets` is readable by exactly the same people. The real fix is per-user identity — speaker recognition — which is a project of its own and the thing that has to exist before HUGO holds anything genuinely private. Recorded here because it is the constraint that decides what is reasonable to tell HUGO, and the calendar and meeting-notes rounds raise the stakes well above a standup time.
